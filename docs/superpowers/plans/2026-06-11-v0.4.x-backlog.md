## Task 1 — Query coercion write-back: expose `req.parsedQuery` (item 5)

**Size:** S (~half day). **Parallelizable:** yes.

**Confirmed current behavior** (read before coding — these are the load-bearing facts):
- Celsian validates `schema.querystring` and writes the coerced result to **`request.parsedQuery`**, not back to `req.query` — `WhatStack/celsian/packages/core/src/app.ts:981–988`:
  ```ts
  if (schema.querystring) {
    const querySchema: StandardSchema = fromSchema(schema.querystring);
    const result = querySchema.validate(request.query);
    if (!result.success) throw new ValidationError(result.issues ?? []);
    (request as Record<string, unknown>).parsedQuery = result.data;
  }
  ```
  (Body, by contrast, IS written back: `request.parsedBody = result.data` at app.ts:978.)
- `parsedQuery` exists at runtime but is only typed on celsian's `TypedCelsianRequest` (celsian `types.ts:127–136`), not on the base `CelsianRequest` that vura re-exports. So vura handlers can't see it without a cast.
- Vura maps `schema.query` → celsian `querystring` in `packages/core/src/runtime/api-app.ts:129–137`. The handler wrapper (`applyThenCompat`, `packages/core/src/compat.ts:48–58`) only shims `body`; it does not touch query — and since celsian sets `parsedQuery` directly on the same request object, **the coerced data is already present at runtime on the object vura handlers receive**. The gap is purely typing + docs.
- Docs are honest about the gap but contain an error: `docs-site/pages/ladder/3-api.md:64–77` says "read `req.query.get('draft') === 'true'`" — wrong, celsian `req.query` is a plain `Record<string, string | string[]>` (celsian `request.ts:50–77`), not `URLSearchParams`. Also says "coercion write-back is planned".

**The fix (smallest surface):** do NOT mutate `req.query` (its type promises strings; coerced numbers/booleans would make the type lie). Instead surface the celsian-native `parsedQuery`:

- [ ] Write a failing test in `packages/core/test/runtime-api-app.test.ts`: register a route with `schema = { query: z.object({ page: z.coerce.number() }) }` (use the existing zod/defineSchema pattern in that test file), handler asserts `req.parsedQuery` equals `{ page: 2 }` (a real number) for `GET /api/x?page=2`, and `req.query.page === '2'` (raw string untouched). Add a second case: invalid query → 400.
- [ ] In `packages/core/src/compat.ts`, extend `ThenRequest`:
  ```ts
  export type ThenRequest = CelsianRequest & {
    body?: unknown;
    /** Validated + coerced query (set by celsian when a `schema.query` is declared). */
    parsedQuery?: unknown;
    validated?: { body: unknown; query: unknown; params: unknown };
  };
  ```
  No `applyThenCompat` change needed — verify the test passes against the property celsian already set.
- [ ] Decision point for the implementer: if the test reveals `parsedQuery` is NOT present (e.g. celsian version skew), the fallback is to set it in the wrapped handler in `api-app.ts:124–125` from a celsian hook — but at @celsian/core 0.5.2 (the pinned version) the write at app.ts:987 is confirmed present.
- [ ] Update `docs-site/pages/ladder/3-api.md` (lines ~55–80): replace the incorrect `req.query.get('draft')` advice with `req.parsedQuery`; delete "coercion write-back is planned"; show the typed access pattern. Check `docs-site/pages/reference/route-kinds.md` for any echo of the old wording.
- [ ] Verify: `pnpm vitest run packages/core/test/runtime-api-app.test.ts` then full `pnpm vitest run`.
- [ ] Commit: `fix(core): surface validated query as req.parsedQuery; correct query docs`.

**Spec (smallest surface — per-route config only, no vura.config key):**
- [ ] Failing unit tests in `packages/core/test/hot-routes.test.ts` for a new pure helper `isOriginAllowed(origin: string | undefined, allowlist: string[] | undefined): boolean` in `packages/core/src/runtime/ws-upgrade.ts` (new file; re-export from `runtime/hot.ts` or `index.ts`):
  - `allowlist === undefined` → `true` (backward compatible: unset = current accept-all behavior).
  - `origin === undefined` with an allowlist set → `true`, and document why: browsers always send Origin on WS handshakes; CSWSH is a browser attack, and non-browser clients can forge any Origin anyway. (State this in the JSDoc — reviewers will ask.)

- [ ] Implement in `server.ts`: after the route match succeeds (insert around line 581, before the 404 branch's `handleUpgrade`), read `(matchedRoute.config as any).origins`; on rejection:
  ```ts
  socket.write('HTTP/1.1 403 Forbidden\r\nConnection: close\r\n\r\n'); socket.destroy();
  ```
- [ ] Docs:
  - `docs-site/pages/reference/route-kinds.md` — add `origins` to the hot-route config table (near the `websocket(peer, req)` contract at lines 49–69) with the default-open caveat.
  - `docs-site/pages/ladder/4-hot.md` — add a short "Restrict origins in production" section recommending `origins: ['https://yourapp.example']` for any cookie-authenticated app.
